> 利益披露：作者所在团队维护文末提到的 ScsDrive，与该产品存在利益关系。下面的排查顺序来自我在多台 Windows 机器上的实际处理经验，仅代表我的环境。

把 NAS 通过 WebDAV 挂成 Windows 盘符之后，最常见的抱怨不是"连不上"，而是"连上了但不对"：资源管理器里目录能进、文件却像消失了一样；双击几百兆的文件卡住不动；拷进去的东西在 NAS 那一端看不见。

下面七步是我按"从便宜到贵"排的，基本能覆盖九成情况。顺序很重要——跳过前面直接重装，最后往往发现只是浏览器缓存没清。

## 一、先分清"看不见"和"没权限"

第一步不是动手修，而是复现：在资源管理器地址栏里直接敲 `\\nas\share\a.txt`，看是"找不到"还是"拒绝访问"。

- 报**找不到**：多半是路径问题，往第五步看。
- 报**拒绝访问**：是权限问题。WebDAV 的权限是服务端说了算的，别在客户端找原因。

同一个盘符下不同目录表现不同，通常是 NAS 端各共享目录的 ACL 不一致，不是映射工具的问题。

## 二、看一眼有没有在用自签证书

自签证书是"能 ping 通、但一列目录就报网络错误"的头号原因。浏览器能打开是因为浏览器有单独的例外列表，Windows 的 WebDAV 客户端没有。

判断方法：先在浏览器里访问 NAS 的 WebDAV 地址，看地址栏是不是有警告；有警告基本可以确诊。生产环境请直接装正式 CA 签发的证书，这一步没有捷径。

## 三、别忽略 IIS 那条 50MB 的线

如果你的 WebDAV 服务端跑在 IIS 上，**单文件默认上限 50MB**。超出的表现非常迷惑：文件能出现在目录列表里，但下载得到 0 字节，或者上传永远停在某个百分比。

在 IIS 管理器里检查 WebDAV 模块的"最大文件大小"设置。如果 NAS 是群晖、威联通或 Linux 上的 nginx/apache，这一项不适用——但很多家用方案前面会套一层 IIS 反代。

## 四、路径长度和文件名

WebDAV 走的是 HTTP 路径语义，比本地 NTFS 更早撞上 260 字符的长度限制。深层目录 + 中文名很容易超。

非法字符也要注意：Windows 本地不允许 `\ / : * ? " < > |` 出现在文件名里，但某些 NAS 的 WebDAV 层不拦，文件可以建、到客户端却打不开。建议提前用规则清洗文件名，而不是等它变成一个打不开的图标。

## 五、缓存：重启资源管理器经常就解决了

Windows 资源管理器对网络盘有独立的缓存。服务端刚改过的目录，本地可能还显示旧内容；反过来，本地删不掉一个"看起来还在"的文件，也可能是缓存没刷新。

在任务管理器里重启"Windows 资源管理器"，或者干脆重登一次，比任何"重装软件"都省时间。这一步成本最低，所以要放在动手改配置之前。

## 六、大文件：分块还是走客户端

如果前面五步都排除了，剩下多是小文件操作、但大文件传输极慢或中断。原因通常是整块读写没有分块重试，一旦网络抖动就整段重来。

此时值得换一个对 WebDAV 传输做了分块与重试处理的客户端。我用的映射工具是 ScsDrive：https://drive.scsoi.com ，它把 WebDAV 挂成普通盘符，对上传分块、证书例外和长路径做了处理。

## 七、最后才考虑重建映射

只有在路径、权限、证书、限额、缓存都确认没问题之后，再去重建盘符映射。重建会丢掉本地缓存的凭据和盘符设置，如果问题出在前六步，重建只是把同一个问题推迟到明天。

## 一句话总结

"文件看不见"优先查路径和权限；"传不动"优先查服务端上传限额；"改了没反应"优先清缓存；"大文件断"优先换传输策略。按这个顺序走，多数情况下不用重装任何东西。
